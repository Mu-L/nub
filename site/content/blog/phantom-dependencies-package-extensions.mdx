### What are package extensions?

These "extensions" allow package managers to inject a package's undeclared dependencies and peer dependencies into their resolution algorithms in cases where they are omitted. Unfortunately this is true across a vast swath of (dare I say it) load-bearing packages. This fundamental unsoundness is inherent to npm and is the cause of many an `ERR_MODULE_NOT_FOUND`.

They look like this:

```js
export const packageExtensions = [
  [
    '@nrwl/devkit@*',
    {
      dependencies: {
        tslib: '*',
      },
    },
  ],
  // ...
];
```

<Accordion title="What is a phantom dependency?">

A package imports something its manifest never declares. Under a flat `node_modules`, that import can happen to work because an unrelated dependency installed the missing package higher up the tree.

A global virtual store moves the importing package outside the project. Node follows its symlink to the real location, where the project's `node_modules` is no longer an ancestor. The undeclared import stops resolving. Yarn Plug'n'Play also rejects undeclared imports rather than relying on the flat-tree accident.

### How does this compare to Yarn's database?

For the last several years, the Yarn-maintained `@yarnpkg/extensions` package has been used by [Yarn](https://github.com/yarnpkg/berry/pull/733) to improve module resolution for Plug'n'Play. More recently, this package now undergirds the [Aube](https://github.com/aubepkg/aube/pull/1369) and [pnpm v12](https://github.com/pnpm/pnpm/pull/12372) global virtual stores.

> Bun 1.4 shipped an opt-in [global virtual store](https://github.com/oven-sh/bun/pull/29489), but it ships without extension-based patching at all. Packages with undeclared dependencies can install successfully, only to fail with `MODULE_NOT_FOUND` at runtime.

Here's the problem: it's woefully incomplete and minimally maintained—just a few in the last three years.

| Database | Packages |
| --- | ---: |
| `@yarnpkg/extensions@2.0.7` | 142 |
| `@nubjs/extensions@1.0.3` | 792 |

The new `@nubjs/extensions` package serves as a modern, 100%-compatible drop-in replacement.

- **Every Yarn rule is preserved**, including its dependency ranges and peer metadata.
- **The export format is unchanged:** `packageExtensions`, an array of `[selector, extension]` pairs.
- **CommonJS and ESM are supported.**

### How can other tools use this?

```diff
import {
  packageExtensions,
- } from '@yarnpkg/extensions';
+ } from '@nubjs/extensions';
```

Package-manager authors can consume the export directly. Individual projects can use the ready-to-use Yarn and pnpm configuration in the [package documentation](/docs/install/extensions), which also covers optional dependencies and contributing corrections. Installing the npm package alone doesn't replace a package manager's bundled database.

Nub already uses the database to repair known omissions during resolution. Its install-time detector handles undeclared imports too, with cached results to avoid scanning unchanged package contents again.

### How is the database updated?

- **Daily scans** check current published package versions.
- **Daily publication checks** release a new patch version only when the extension rules change.
- **Public scan records** include version-specific evidence and [weekly npm download estimates](https://github.com/nubjs/package-extensions/blob/main/inputs/downloads.json) in the [repository](https://github.com/nubjs/package-extensions).

The database combines generated results with a fixed, handwritten core:

- **Dynamic imports can need handwritten rules** when the package name is computed at runtime, as in `import(packageName)` or `require(packageName)`.
- **Most generated additions are optional peers.** A React adapter should declare its relationship with React without forcing every user of the package to install it.
